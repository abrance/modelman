# 工作台骨架设计

本页是工作台（model-agent）的骨架设计：骨架来源（fork pi-web）、卷布局、能力资产的加载与覆盖、
对外端点、会话与物料的数值。上游是 `docs/platform.md` 的 P1–P15，本页把它们写到能直接开工的粒度。

**边界**：工作台实现落在独立仓库，本页在仓库落地时整页迁走。本仓库只管能力与契约，
不写部署脚本（口径同 `docs/deployment.md`）；本页列的是"需要 cops 配合什么"，不是部署步骤。

## 骨架：fork pi-web，不自建第二套 HTTP 层

工作台的壳用 `@agegr/pi-web`（MIT，Next.js）的**源码 fork**，不从零写 HTTP 层。理由：
面 A（会话列表、续聊、分支、工具调用渲染、上下文与花费展示）与面 B 的一部分（provider 与
API key、模型、插件包、skills 面板）它已经做了，而这些正是自建里最耗时也最不值得重写的部分。

```
浏览器
  │ HTTPS（TLS 由主机反代终结）
  ▼
pi-web（fork；UI + API routes，唯一对外进程）
  │  内嵌 Pi SDK（AgentSession），不起 RPC 子进程
  ▼
云端 provider（HTTPS）
  │
  └ 读写的都是卷：组件目录、会话、能力、物料
```

| 选择 | 理由 | 代价 |
|---|---|---|
| fork pi-web 而不是自建 | 面 A 与部分面 B 白拿；它的密码鉴权本就是为"反代 + 公网"写的 | 跟随上游升级；Next.js 的体积与内存；形态分叉风险 |
| 内嵌 Pi SDK（随上游架构），不起 RPC 子进程 | 与上游一致，改动面最小 | 隔离从"进程"降到"服务重启"：extension 崩了会带走 UI 进程，靠 P12 的发布确认 + 留痕 + 失败回退与服务重启兜住 |
| 沿用它的既有约定，不另起一套 | 它直接读组件目录（`PI_CODING_AGENT_DIR`），会话落在组件目录的 sessions 子目录下 | 会话与配置格式跟随上游，升级需回归 |

**分叉控制**：服务端改动集中在我们新增的 API routes 与少量共享库触点；能不改源码的地方用它
已暴露的下游钩子（会话行右键菜单事件、会话存活登记），减少与上游的冲突面。

注意：npm 包只发布构建产物（`bin`、`.next`、`public`），要加服务端 API routes 必须 fork 源码仓库。

## 卷布局

一个 PVC 挂到 `/data`，镜像里的基线放只读的 `/opt/agent-seed`。

| 路径 | 内容 | 来源 | 谁写 |
|---|---|---|---|
| `/data/agent-home` | Pi 组件目录（`PI_CODING_AGENT_DIR`）：settings、安装好的包、模型缓存 | 首启从 seed 初始化 | pi-web 与 Pi |
| 组件目录的 sessions 子目录 | 会话 JSONL（按工作目录分组） | 运行期 | pi-web 与 Pi |
| `/data/skills` | 用户写的 skill | 平台内 | pi-web 与我们的 API routes |
| `/data/extensions` | 用户写与发布的 extension、历史版本 | 平台内 | pi-web 与我们的 API routes |
| `/data/artifacts` | 物料：输入、产物、导出记录 | 运行期 | 我们的 API routes |
| `/data/overrides` | provider 覆盖、发布留痕、基线 manifest | 运行期 | 我们的 API routes |

要点：**组件目录必须可写且落在卷上**（Pi 自己会往里写东西）。所以镜像里的基线是只读的种子，
不是最终位置——否则 Pod 一重启就把平台内写的能力和会话一起丢了（P1）。

## 能力资产：加载与覆盖（P1 / P7 落地）

### 启动序列

```
1. /data/agent-home 不存在 → 从 /opt/agent-seed 复制，写 manifest（记录每份文件的基线哈希）
2. 每份 seed 文件按三类处理：
   - 卷上不存在            → 复制过去
   - 卷上存在且哈希 == 旧基线 → 用新基线覆盖（说明没被人改过）
   - 卷上存在且哈希 != 旧基线 → 保留本地版，标记 conflict，界面提示"该能力已被本地修改"
3. 更新 manifest 里的基线哈希，供下次比较
4. 起服务，等就绪探针通过，失败按"回退"处理
```

判定"被本地改过"靠的是 manifest 里记的**上次基线哈希**，不是文件时间：时间戳在镜像重建、
卷迁移、时间跳变下都不可靠。

### 加载方式

- 能力目录在 Pi 的 settings 里**显式列出**（`skills` 数组 + extension 所在目录），
  不依赖隐式全局发现——运行时能力集必须一眼看得见、跟镜像与卷的归属清晰对应。
- `PI_OFFLINE=1` 与版本检查关闭：运行期不允许任何安装或更新动作（口径同 modelman
  不在运行期下载权重）。

### 发布与回退（级 1 / 级 2）

| 级 | 动作 | 生效 | 回退 |
|---|---|---|---|
| 1 skill | 保存即写 `/data/skills` | 让 Pi 重新加载（必要时重启服务） | 保留本地版；可"恢复出厂" |
| 2 extension | 先存草稿，**一次确认发布**后才写 `/data/extensions` | 重启服务 | 重启失败 → 自动回到上一可用版本 |
| 3 新服务 | 平台内只产出草稿目录与导出包 | 不在平台内 | 走 `docs/adding-a-service.md` 出镜像 |

级 2 的实现细节：

- 每次发布写一份发布记录（时间、文件名、内容哈希、上一版标识）到 `/data/overrides`。
- **保留最近 5 个版本**，更旧的按序回收。
- 就绪判据：服务启动成功且存活探针通过；失败即回退到最近一个自检通过的版本，并记录原因。

## 对外端点

面 A 与部分面 B 由 pi-web 提供，不自建第二套；我们新增的是面 C、级 2 的发布与回退、
基线冲突提示，以及一个免登录的存活探针。

| 面 | 来源 | 说明 |
|---|---|---|
| 面 A 会话 | pi-web | 列表/详情/发送/事件流/分支/导出/花费展示都在它的 UI 与 API routes 里 |
| 面 B 能力（一部分） | pi-web | provider 与 API key、模型、插件包、skills 面板；它的写入落点就是组件目录（卷） |
| 面 B 能力（剩余） | 我们新增 | 基线冲突提示、级 2 发布与回退、级 3 草稿导出 |
| 面 C 物料 | 我们新增 | 归档、导出/导入、用量与回收 |
| 运维 | 我们新增 | 免登录存活探针，供 cops 探针使用 |

### 我们新增的端点

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/livez`、`/healthz`、`/readyz` | 免登录探针。前两个只看进程活着；`/readyz` 真的去碰组件目录与对账 manifest，对账没跑成就 503 |
| GET | `/abilities` | 能力清单：来源（基线/用户）、哈希、冲突状态 |
| GET | `/abilities/conflicts` | 被本地改过、且基线已更新的能力 |
| POST | `/abilities/skills/{name}/restore` | 恢复出厂版本（skill 的日常读写用 pi-web 面板） |
| POST | `/abilities/extensions` | 保存草稿 |
| POST | `/abilities/extensions/{name}/publish` | 发布（一次确认） |
| GET | `/abilities/extensions/{name}/versions` | 版本与发布记录 |
| POST | `/abilities/extensions/{name}/rollback` | 回退到指定版本 |
| GET | `/abilities/services/drafts` | 级 3 草稿：产出物与导出 |
| GET | `/artifacts` | 物料列表（按日期与会话分桶） |
| GET | `/artifacts/{id}` | 物料详情 |
| POST | `/exports` | 打包导出（会话或物料） |
| GET | `/exports/{id}` | 下载导出包 |
| POST | `/imports` | 导入导出包 |
| GET | `/storage` | 用量与回收状态（会话、物料、能力各占多少） |
| POST | `/storage/gc` | 手动触发回收 |

### 错误结构

所有错误响应带可读的 `error` 字段（与 modelman 服务契约口径一致），状态码沿用
`400 / 401 / 404 / 409 / 413 / 429 / 503`。

导出包格式：单个压缩包，内含 manifest（版本、导出时间、来源会话）、会话原文、物料文件。

## 数值（现在就得给）

| 项 | 值 | 归属 |
|---|---|---|
| 会话与物料保留 | 90 天 | P10 |
| 物料目录上限 | 2 GB，超限按最旧回收 | P10 |
| 回收执行时机 | 启动时 + 每次会话结束后惰性执行 | 不引入常驻调度（P14） |
| extension 保留版本数 | 最近 5 个 | 本页 |
| 登录 cookie 有效期 | 上游自带：30 天，HttpOnly + SameSite=Lax（协议是 https 时加 Secure）——已核对源码，不改 | 上游 `lib/web-auth.ts` |
| 登录失败限制 | 上游自带：指数退避 1s 起、封顶 60s、失败 5 分钟无新失败则重置（API 的 Basic 且每个请求都算一次尝试，共用同一计数器）——已核对源码，不需要外层限速 | 上游 `lib/auth-throttle.ts` |
| 会话并发 | 1（单用户：同一进程内多会话串行推理） | 本页 |
| 出网并发 | 上限可配，默认 2 | 本页 |

写不出数值的路径不写（`docs/architecture.md` 推理侧第 4 条约束同样适用于这里）。

## provider 配置（P8 落地）

覆盖入口白拿：pi-web 的 Models 面板就是改 provider 与 API key 的地方，写入落点就是它的
配置与凭据存储（在组件目录里，也就是卷上）。我们要补的只有两件事：冲突判定与回显掩码。

| 字段 | 来源 | 是否下发浏览器 |
|---|---|---|
| base URL | 覆盖或环境 | 是 |
| api key | 覆盖或环境 | **否**，只回显掩码 |
| 模型清单 | 覆盖或环境 | 是 |

覆盖配置文件写在 `/data/overrides`，权限 `0600`。密钥永远不进仓库、不进镜像层、不进浏览器。

## 鉴权（P9 落地）

- 沿用 pi-web 的密码鉴权（环境注入单密码），不另做一套登录。
- 它的主机名白名单用来配合主机反代：TLS 在反代终结，白名单里写对外域名。
- 落地时要核对两件事：登录失败的限速、会话 cookie 的时效；缺哪样就在外层补（见上表）。
- 只做密码意味着"登录 = 全部权限"，这是单用户产品的有意选择，不是简化未完成的部分。

## 小模型接缝（P5 落地）

本阶段**不接** ocr / logcluster。骨架里保留接缝：

1. 工具清单有一个统一的来源抽象（现在为空实现）。
2. 能力清单页显示"未接入"状态，而不是隐藏入口。
3. 待把各服务 API 规整为统一形态（统一错误结构、能力清单聚合、上限声明、接口描述、
   鉴权开关）之后，工具由接口描述派生，不手写第二份。

## 仓库形态与与 modelman 的整合

### agent 仓库是什么

agent 仓库 = **pi-web 的 fork**，不是新写的空仓库。

| 项 | 约定 |
|---|---|
| 上游 | `agegr/pi-web`（MIT），保留 upstream remote |
| 我们的代码 | 只放固定目录（平台 API routes、面 C 页面与逻辑、seed 与镜像构建文件） |
| 上游文件 | 只做最小触点，且每处登记在分叉登记表里 |
| 同步方式 | 上游发版时 merge 上游，按分叉登记表逐个处理冲突 |

分叉面收敛在固定目录的好处：将来若要脱离 pi-web 自建，把自己的目录整体搬走即可，
不用从上游代码里挑自己的东西。

#### 分叉登记表（权威在 agent 仓库）

登记表跟着仓库走，单一份，在 agent 仓库的 `platform` 目录下的 FORK.md 里（不在这里再拄一份，
阻止两边各自漂）。截至切片 1，实际登记的是：

| 文件或目录 | 性质 | 改动的理由 |
|---|---|---|
| `platform/` | 我们的目录（新增） | 基线、启动对账、镜像与冒烟；完全不碰上游 |
| `app/livez`、`app/healthz`、`app/readyz` | 新增 | 免登录探针；上游 middleware 的 matcher 不覆盖这三个路径 |
| `.dockerignore` | 新增 | 构建上下文瘦身 |
| `app/layout.tsx` | **改上游** | 字体从 `next/font/google` 换自托管（构建期不许访问 Google Fonts） |
| `package.json` 与 lockfile | **改上游** | 新增自托管字体依赖 |

### 构建与镜像归属

| 项 | 值 |
|---|---|
| 在哪构建 | **agent 仓库自己的 CI**（即 fork 仓库的 GitHub Actions）。镜像 = 上游代码 + 我们的目录，只有 fork 同时持有两者 |
| 镜像名 | `ghcr.io/abrance/model-agent` |
| tag | 按 modelman 的服务前缀口径打 `agent/vX.Y.Z`，镜像 tag 为 `vX.Y.Z-<提交短 sha>`，不可覆盖 |
| cops 侧 | 单元 `apps/model-agent`，固定在 `.env` 里的镜像 tag |
| 冒烟 | 与 modelman 的 `smoke.sh` 同形态，**不出网**、不调云端 provider。切片 1 已实现七步：探针、未登录被挡、登录后页面可用、容器内基线校验、重启后平台内写的 skill 还在、被本地改过的基线文件不被静默覆盖且记进冲突 |
| Pi 本体 | 不另装全局副本：运行期的 `pi` 命令指向应用依赖里的同一份 CLI（结构上不可能版本漂移），当前 0.87.1，由 agent 仓库的 lockfile 决定 |
| 体积 | 切片 1 实测 1.51 GB。再瘦的杠杆是 Next 的 standalone 输出，要改启动方式，单独一个改动做 |
| 上游 merge 后 | 走同一条流水线，冒烟当作合并门禁 |

为什么不在别处构建：另建一个仓库就只能二选一——要么把上游源码 vendored 进来（每次上游更新
要手工同步，fork 的 merge 能力白扔），要么依赖 npm 包（而 npm 包只发构建产物，加不了服务端
API routes，见上文），面 C 就实现不了。所以是**一个仓库、一条流水线、一个镜像**，不多不少。

镜像名不带 `modelman-` 前缀，是刻意的：它不在 modelman 的服务集合里，不参与
`services/*/service.mk` 的发现，也没有 `registry/` 条目。

附带一个好处：构建地点不随 fork 关系变化。将来若真脱离 pi-web 自建，还是这个仓库、这条
流水线——因为我们的目录本来就是自包含的（见分叉登记表）。

### 分支与上游同步

| 项 | 约定 |
|---|---|
| main | 产品主干。上游以 `upstream/main` merge 进来，平台代码与平台改动都落在 main 上 |
| 功能分支 | 短命（`feat/...`），走 PR 进 main。**分支名不要与目录同名**，免得"分支"与"代码位置"混淆 |
| 分叉面 | `git diff --stat upstream/main...main` 一条命令就能看出我们改了上游哪些文件；这张清单应与分叉登记表一致，不一致就说明有人没登记 |
| 起点现状 | fork 的 main 与 upstream/main 完全一致（零分叉），是开始加平台代码的最干净起点 |

### 与 modelman 的三条接缝

不共享代码（两个仓库语言都不同），只共享三件东西：

| 接缝 | 权威在哪 | agent 侧怎么用 |
|---|---|---|
| 约定 | modelman 的 `docs/deployment.md` 与 `docs/architecture.md` | 不复制文档，引用即可：tag 命名、健康端点、错误 `error` 字段、冒烟形态同口径 |
| 能力清单 | modelman 的服务与 `registry/<name>.yaml` | 只当消费方：读各服务对外接口描述与能力清单，不反向写 |
| 交付形态 | 各自的 CI | 两个仓库各自出镜像，cops 各自固定 tag |

**单向依赖，无环**：agent 依赖 modelman 的能力，modelman 不知道 agent 存在。这是两边能各自
独立发版、独立回滚的前提——modelman 的 CI 与契约测试里不该出现任何 agent 相关的东西。

### 不进 modelman 仓库的理由

| 选项 | 为什么不 |
|---|---|
| 放进 `services/agent/` | 会撞上 modelman 的服务发现规则（按目录找 `service.mk`、要求 `registry/<name>.yaml` 与契约测试），而 agent 不是模型服务：没有权重、没有契约基线 |
| modelman 改成装下两者的单仓 | 构建链、CI 缓存、镜像体积、密钥面全部混在一起；modelman 的"一个服务一个镜像、运行期无外网"口径会被 agent 的"有状态 + 需要外网"污染 |
| 把 fork 作为 modelman 的子目录 | fork 要能持续 merge 上游，放进子目录会把上游历史与 modelman 历史缠在一起 |

### 本地跑起来与跨仓测试

| 项 | 归属 |
|---|---|
| 本地起 agent（含卷、seed、密码） | agent 仓库自己的 dev 脚本 |
| 跨仓集成测试（agent 对小模型服务） | 本阶段不做（P5 不接小模型）；要做时在 agent 仓库的 CI 里按 tag 拉起 modelman 的服务镜像，不在 modelman 仓库里跑 |
| 端到端冒烟 | 与 modelman 的 `smoke.sh` 同形态，各自一份，不互相引用文件 |

### 什么时候重新评估

出现下列信号之一再回头看这个划分：agent 要脱离 pi-web 自建、出现第二个消费 modelman 能力的
系统、或者跨仓改动频繁到需要同步发版。

## 第一版镜像的能力基线（v1）

原则：**基线越小越好**。镜像基线是要 review、要跟上游 merge、每次重建都要验的东西；
其余能力走卷按需加（P1 两段式）。所以 v1 只放"没有它就不算工作台"的那几个。

### 进基线

| 能力 | 形态 | 为什么必须在基线里 |
|---|---|---|
| MCP 适配 | 包 | 接模型能力的唯一通道，也是 P5 的接缝；以后接小模型靠它 |
| 跨会话记忆与会话搜索 | 包 | 记忆落点就在组件目录（卷），是面 C 归档的上游；单用户助手的价值高度依赖能记得住 |
| 成本可见 | 包 | 产品面 A 的硬要求：一次回答能看出花了多少 |
| 写 skill | skill | 面 B 的核心动作，没它平台内就长不出新能力 |

### 建议带（有需求就带）

| 能力 | 理由 | 代价 |
|---|---|---|
| 联网（搜索、抓取、PDF、转录） | 单用户助手的常见需求 | 数据出境，必须在面 A 看得见 |
| 编码纪律 | 面 B 写 extension 本质是写代码 | 会改变输出风格 |
| LSP | 写 extension 时的类型与诊断 | 需要语言服务器二进制进镜像 |

### v1 不带（附触发条件）

| 不带 | 原因 | 什么时候加 |
|---|---|---|
| 浏览器自动化 | 容器要装 chromium 与 ffmpeg，镜像涨几百 MB | 真出现页面自动化需求 |
| 子代理编排 | 复杂度，单用户 v1 不值 | 出现可并行的独立子任务 |
| provider 用量/余额面板 | 与成本可见重叠 | 需要看账户额度时 |
| 桌面 GUI | 与 Web 入口冲突 | 不用 |
| 侧问命令、文件范围附件 | 交互便利而非能力 | 随时 |
| 设计面试类 | 属开发流程 | 不用 |
| bash 命令重写 | 依赖宿主机的一个 CLI 二进制；省 token 发生在 bash 密集的编码会话里 | 工作台真变成编码场景时 |
| 开发机与内网工作流类 skills | 运行时用不上，且带内网依赖 | 不用 |

### 迁移的两个坑

| 坑 | 现象 | 处理 |
|---|---|---|
| skill 是符号链接 | 本机的跨 harness skill 目录指向别的仓库，镜像里没那个路径，链接就断了 | 进基线时**解引用实体拷贝**，并同时检查它引用的脚本与资源 |
| skill 脚本依赖开发机工具 | skill 在，但里面的脚本跑不起来 | 迁移时逐个跑一次；跑不了的宁可不带，或在 skill 里写明依赖 |

### 落法

| 项 | 做法 |
|---|---|
| 清单位置 | 基线清单落在 agent 仓库的 `platform/seed` 目录：`agent-home` 里的 settings 是**唯一机器可读清单**（包与 skill 两个数组），README 只写"为什么"，不抄一遍清单 |
| 版本 | 每个包写字面版本并 pin（同 P16 的包固定口径）；Pi 本体不单独 pin——它由应用依赖的 lockfile 定，且镜像里只有一份 |
| 位置 | 基线能力进镜像的只读种子目录；运行期用户新增的落卷 |
| 校验 | 同目录有一个校验脚本，把关三件事：每条都带字面版本、已安装版本与 pin 一致、skill 不是符号链接（链接进镜像会断）。它在本地正例、把版本改坏、把 skill 换成链接三种情形下都验过 |
| 冒烟 | 镜像冒烟调一次这个校验，少一个包或多一个版本就失败——避免构建脚本改坏了没人发现 |

## 本阶段不做

对接现有小模型、能力市场、多用户与权限分级、沙箱隔离、常驻定时任务、面向程序的接口
（端点复用，见 `docs/platform.md` P13）。

另外两条是随 fork pi-web 一起定下来的：不自建第二套会话面（面 A 归上游），也不在上游
源码里做我们不需要的改动（分叉越浅，升级越便宜）。
