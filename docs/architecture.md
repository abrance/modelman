# 架构与约定

本页是仓库内的落地约定：目录职责、服务内部分层要求、推理侧硬性约束，以及与部署仓库的边界。
系统级设计（要解决什么问题、受什么约束、为什么这么选）见 `design.md`；
后续计划见 `roadmap.md`。

## 为什么是一个仓库

服务代码、模型文件和交付配置放在同一个仓库，而不是拆成"基础镜像仓库 + 服务仓库"。

理由：小模型的权重体积在几十 MB 以内，代码与权重必须同时变化才能保证可复现；
拆成两个仓库会引入跨仓库版本对齐问题，而这个问题没有换来任何好处——
`cops` 侧只关心镜像 tag，不关心仓库怎么划分。

仓库数量不等于交付产物数量。一个仓库可以产出多个镜像（基础镜像、权重镜像、服务镜像），
需求出现前不要提前拆分。

## 交付形态

每个服务一个镜像，一个镜像只含一个服务。原因：

1. 镜像层可复用，换模型只重推变化的层。
2. 每个服务可以独立回滚。
3. 资源上限可以按服务设置，而不是按"所有模型"设置。

权重直接烘进镜像，不在运行时下载。原因：

1. 构建机可以访问外网，运行环境（云主机）不保证能访问模型站点。
2. 运行时下载会让冷启动时间不可预测，也让"这个容器跑的是哪个权重"变得不可复现。

## 服务内部结构

以 `services/ocr` 为例，四层职责分明：

| 文件 | 职责 |
|---|---|
| `src/config.rs` | 环境变量解析与模型清单，是唯一读环境变量的地方 |
| `src/engine.rs` | 引擎生命周期与推理，负责加载、限流、尺寸约束、解码 |
| `src/api.rs` | HTTP 层：路由、请求校验、响应结构、鉴权、错误码映射 |
| `src/metrics.rs` | Prometheus 暴露，零外部依赖 |

服务目录里另有两个与具体技术栈无关的约定文件：

| 文件 | 职责 |
|---|---|
| `service.mk` | 声明 `SERVICE_BUILD` / `SERVICE_TEST` / `SERVICE_RUN` / `SERVICE_SMOKE` / `SERVICE_FIXTURES` / `SERVICE_CLEAN`，根 `Makefile` 与 CI 据此分派 |
| `smoke.sh` | 容器冒烟检查，CI 与发布流程共用同一份 |

分层要求：

1. 环境变量只在 `config.rs` 读取，便于测试时直接构造配置结构体。
2. 推理只在 `engine.rs` 发生，`api.rs` 不直接接触推理后端。
3. 协议结构体不依赖推理后端的类型，避免后端升级冲刷接口。

## 推理侧的关键约束

这三点是从前一代实现的问题中反推出来的，新增服务时同样适用。

1. **推理必须放阻塞线程。** CPU 推理是同步且长时间的，直接在异步 handler 里调用会占住
   运行时工作线程。
2. **锁的粒度必须到引擎。** 用一把全局锁保护所有模型，会让不相关的模型互相排队，
   连健康检查都可能被在途推理挡住。
3. **并发必须有上界。** 云主机 CPU 是与其它服务共享的，请求堆积比快速失败更糟。
4. **凡是占用磁盘或内存的逻辑，都必须能指出限制它的那个数值。** 别问"正常输入会不会
   超"，只问"最坏输入能占多少"。按四类逐个指：单次输入体积上限、解码或中间结果的内存
   峰值上限、落盘的东西（临时文件、缓存、状态卷）的容量或回收机制、以及并发数——
   并发乘单次峰值才是总数。指不出数值的，要么先在设计里写清回收机制，要么就不写这条
   路径。这条不是洁癖：模型服务最容易出的故障不是算错，而是被一个畸形输入撑爆内存，
   或者日积月累把宿主机根分区写满，两种都不在业务日志里留下明显痕迹。
   对照：`services/ocr` 的闸门与磁盘增长点列在 `services/ocr/README.md`；
   宿主机侧的日志与镜像回收窗口归 `cops`。

## 契约测试

契约测试是模型服务与普通服务最重要的差别：编译通过不代表模型行为没退化。

机制：

1. `tests/fixtures/` 存固定样本与基线文件（`<样本>.expected.json`）。
2. 基线由 `gen-fixtures` 生成，内容是逐行的识别文本与置信度、原始行数、延迟。
3. 测试逐样本比对：行数必须一致，文本相似度必须达到基线里声明的阈值，
   原始检测行数必须一致（否则说明检测阶段变了）。
4. 汇总层再检查 p95 延迟不超过基线的 6 倍——故意放宽，用来捕捉量级退化而不是抖动。

基线变更必须走 review，因为改基线等于改验收标准。

## 与部署仓库的边界

| 事项 | 归属 |
|---|---|
| 服务代码、模型、Dockerfile、镜像发布 | 本仓库 |
| 云主机上的期望状态、端口、资源上限、健康检查参数 | `cops` 仓库 |
| 运行期密钥 | 云主机 `/opt/cops/secrets/`，由 cops 注入 |
| SSH、compose 执行、容器编排 | `cops` 仓库 |
| 公网入口（TLS、域名反代） | 主机上的 dockpanel/traefik，不在两个仓库范围内 |

本仓库不写任何部署脚本，`cops` 不写任何模型逻辑。
