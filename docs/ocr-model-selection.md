# 模型档位实测

本页记录三个 PP-OCR 档位在同一批固定样本上的实测结果，用于决定默认档位，
并作为"什么情况下值得换档"的依据。

## 测量条件

- 样本：`services/ocr/tests/fixtures/` 下 20 张真实截图（小尺寸 UI 文本、中文昵称、数字、形如 `5/60` 的复合文本）
- 硬件：12 核 x86_64 开发机，CPU 推理，`MAX_CONCURRENCY=1`
- 阈值：`CONF_THRESHOLD=0.3`
- 后端：MNN 预编译归档（cpu，未启用 vulkan）
- 复现命令：`cargo run --release --bin gen-fixtures <目录> <档位>`

## 汇总

| 档位 | 识别到的行数 | p50 | p95 | 进程峰值 RSS |
|---|---|---|---|---|
| `v6small`（默认） | 20 / 20 | 6.5 ms | 16.9 ms | 83 MB |
| `v6tiny` | 12 / 20 | 1.2 ms | 4.4 ms | 33 MB |
| `v5` | 19 / 20 | 7.5 ms | 13.9 ms | 75 MB |

结论：`v6small` 在几乎没有额外延迟的前提下明显优于另外两档，作为默认。
`v6tiny` 只适合内存或延迟极紧且可接受漏识的场景。`v5` 保留用于保持输出兼容。

## 为什么没有 PP-OCRv6 medium

上游提供的 `PP-OCRv6_medium_det.mnn` 与 `PP-OCRv6_medium_rec.mnn` 在 MNN 中加载失败：

```
MnnError(ModelLoadFailed("Engine creation failed"))
```

该失败在同一批模型文件的原始工具链中同样可复现，属于模型转换产物问题，不是本仓库的集成问题。
与其交付一个必然在请求时返回 500 的档位，不如把它从镜像中移除并在
`registry/ocr.yaml` 的 `excluded` 段记录原因。

若要重新启用，先取到能在 MNN 中正常加载的 medium 权重，加入 `models/`，
在 `src/config.rs` 的 `MODEL_TIERS` 中登记，然后用
`make fixtures` 生成基线并 review 结果。
