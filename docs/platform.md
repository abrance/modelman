# 平台形态与分层

本页写"整个平台长什么样"：产品形态、分层与仓库划分、能力资产落在哪里、会话与物料
什么会丢、扩展能力分几级。系统级设计（modelman 这个能力库为什么这么设计）见
`docs/design.md`；仓库内落地约定见 `docs/architecture.md`；交付链路见 `docs/deployment.md`。

## 这份文档的边界

平台由三部分组成，本页只写它们之间的接口与产品形态：

| 部分 | 角色 | 仓库 | 本页的态度 |
|---|---|---|---|
| modelman | 能力库：小模型服务 + 契约 | 本仓库 | **权威**，本页不改它的契约 |
| model-agent | 工作台：会话、能力扩展、物料归档 | 独立仓库 | 只写约定，不写实现 |
| cops | 交付：期望状态、密钥、卷、入口 | `cops` 仓库 | 只写需要它配合的部分 |

明确一点：**工作台不是 modelman 里的第 N 个服务。** 两者生命周期、信任等级、状态形态
都不同（见"为什么必须是两个仓库"），合并会同时毁掉可回滚性与安全边界。
工作台的骨架设计（进程形态、卷布局、能力加载与端点）见 `docs/agent-design.md`。

## 产品形态：一个入口，三个面

```
                    平台入口（登录后可见）
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
   面 A「用」           面 B「做」           面 C「存」
   会话                 能力扩展             物料归档
   大模型 + 小模型       写、发布、生效        导出、导入、保留
```

服务对象是**一个人**：不分用户、不分租户、任何功能都能用。这不是"还没做多租户"，
是明确的产品边界（与 `docs/design.md` 的非目标一致）。

三个面各自的职责：

| 面 | 解决什么 | 关键要求 |
|---|---|---|
| A 用 | 自然语言会话，混合调用大模型与各小模型能力 | 每个回答能看出用了哪个模型、花了多少钱、有没有数据出境 |
| B 做 | 在平台内新增/修改 skill、extension 等能力 | 改动必须活过 Pod 重启；extension 是可执行代码，要留痕 |
| C 存 | 把会话、输入、产物归档并带走 | 至少有一个导出入口；目录有上限与保留期 |

## 分层与仓库

```
┌─ 交付层 ────────────────────────────────────────────────┐
│  modelman 仓库 → CI → 镜像（能力库）                     │
│  model-agent 仓库 → CI → 镜像（工作台）                  │
│  cops：期望状态、密钥、卷、入口                          │
└─────────────────────────────────────────────────────────┘
                          ▼
┌─ 运行层 ────────────────────────────────────────────────┐
│  model-agent 工作台  ──HTTP/OpenAPI──▶  modelman 服务    │
│  （会话、能力、物料，卷）                （ocr / logcluster / …）│
└─────────────────────────────────────────────────────────┘
```

| 层 | 职责 | 交付物 | 回滚单位 |
|---|---|---|---|
| 能力库（modelman） | 权重 + 推理 + 对外契约 | 每服务一个镜像 | 换镜像 tag |
| 工作台（model-agent） | 编排 + 会话 + 能力 + 物料 | 一个镜像 + 卷 | 换镜像 tag（**不动卷**） |
| 交付（cops） | 期望状态、密钥、卷声明、入口 | 期望状态文件 | PR revert |

### 为什么必须是两个仓库

| 维度 | modelman 服务 | 工作台 |
|---|---|---|
| 信任等级 | 无状态、只算模型 | 可执行任意代码（extension、shell） |
| 状态 | 除日志聚类外无状态 | 会话、能力、物料都要落盘 |
| 外网依赖 | 运行期无 | 需要云端 provider API |
| 变更节奏 | 换模型才发版 | 能力随时增改 |

把工作台塞进 modelman 服务镜像，等于让"无状态、可回滚、无外网"的交付约定同时失效。

## 能力资产：镜像基线 + 卷覆盖

这是本阶段最关键的一条决策。工作台的能力（skill、extension、工具清单）有两个来源：

| 来源 | 位置 | 随镜像 tag 回滚 | 平台内可改 |
|---|---|---|---|
| 出厂基线 | 镜像层 | ✅ 会 | ❌ |
| 用户能力 | 卷（`.pi/skills`、`.pi/extensions`） | ❌ **不会** | ✅ |

**为什么不能只放镜像**：面 B 要求"平台内写完能力，Pod 重启不能丢"。只放镜像层，平台内
写的改动会随 Pod 消失；只放卷，出厂能力就失去了版本与回滚。所以两段式：

1. 镜像提供**出厂基线**，随 tag 走，可回滚。
2. 用户新写或修改的能力落**卷**，Pod 重启不丢。
3. 同名时**卷覆盖基线**；每份能力记录来源（baseline / user）与内容哈希。
4. 提供"恢复出厂版本"动作，把被覆盖的基线能力还原。
5. **基线更新到一份已被本地改过的能力时，保留本地版并提示"该能力已被本地修改"**，
   不静默覆盖，也不阻断启动。

这与 `docs/design.md` D13 是同构问题：**运行期状态不属于镜像，回滚镜像不会回滚它。**
日志聚类当年用"schema 校验 + 降级 + 不覆盖旧状态"处理的，工作台用"来源标记 + 覆盖规则 +
恢复动作"处理。

## 会话与物料：什么会丢

| 位置 | 内容 | 容器重启 | 卷丢失 / 换主机 |
|---|---|---|---|
| 镜像层 | 出厂能力、工具清单、工作台本体 | 不丢 | 不丢 |
| 卷 | 用户能力、会话记录、物料目录、provider 覆盖配置 | **不丢** | **丢** |
| 容器内临时目录 | 中间文件、下载、缓存 | 全丢 | 丢 |

归档入口解决的是**第二行的第三列**，不是容器重启——容器重启由卷兜住（日志聚类已经
是这么做的）。最小可用形态：

1. 一个物料目录，按日期与会话分桶。
2. 一个**导出**动作：某会话 / 某物料 → 打包下载。
3. 一个**导入**动作：把包放回去。
4. **容量上限 + 保留期**：保留 90 天，目录上限 2 GB，超限按最旧先回收。写不出数值就不
   写这条路径（`docs/architecture.md` 的推理侧第 4 条约束同样适用于落盘的会话与物料）。

四条之外不做文件管理器、不做版本管理、不做协同。

## 扩展能力：三级，生效路径不同

| 级 | 扩展什么 | 平台内能否完成 | 生效方式 | 留痕 |
|---|---|---|---|---|
| 1 | skill（markdown 知识） | ✅ | 保存即生效或 reload | 记录来源与哈希 |
| 2 | extension（TypeScript 代码） | ✅（需一次确认发布） | 发布后 reload/重启进程；**失败自动回退上一可用版本** | **必须留痕**：谁、何时、改了哪份、哈希 |
| 3 | 新小模型服务 | ❌ | 平台只产出草稿，出服务走 CI 出镜像 | 走 `docs/adding-a-service.md` 检查单 |

三级在界面上必须长得不一样：级 1 是"随手记"，级 2 是"装软件"（有执行权），级 3 是
"上新服务"（不是平台内能做完的事）。

级 2 的留痕不是给别人看的——单用户平台里唯一会忘记"agent 为什么突然会删文件"的人是你自己。

## 模型供给

| 来源 | 阶段 | 形态 |
|---|---|---|
| 云端 provider API | 当前 | 平台读取环境注入的 provider 地址与密钥 |
| 本地大模型 | 后续 | 作为 modelman 的一个新服务（走 `docs/adding-a-service.md`），provider 指向它 |

云端 provider 的地址与密钥由部署侧注入环境，不进任何仓库、不进镜像层；平台内可覆盖修改，
覆盖写卷（环境是基线，不是唯一来源）。模型档位**按会话固定**：创建会话时选定，中途可切，
会话记录里必须能看出哪些内容发给了云端 provider（成本与数据出境两件事都要可见）。

## 鉴权口径

| 面 | 口径 |
|---|---|
| 平台入口 | 需要登录：**只输密码**，凭证由部署侧注入；登录后签发会话 cookie |
| 小模型服务 | 本阶段沿用既有口径：不启用鉴权直接开放（`docs/design.md` D15–D17），统一鉴权在外层做 |
| 云端 provider 密钥 | 只存在于工作台进程环境与卷上的覆盖配置，不下发给浏览器 |

平台入口是唯一带登录的地方，也是后续统一鉴权的落点：入口收敛后，各小模型服务可以从
公网入口摘掉，只允许工作台访问。

## 本阶段明确不做

| 不做 | 原因 |
|---|---|
| 对接现有小模型（ocr / logcluster） | 各服务的 API 需要先规整为统一形态，避免"接一次、改一次" |
| 能力市场、评分、搜索 | 单用户场景下没有意义；能力的形态是文件与包，够用 |
| 多用户、账号体系、配额、计费 | 与 `docs/design.md` 的非目标一致 |
| 沙箱隔离 | 单用户先不隔离，但级 2 的发布动作必须留痕 |
| 在平台内完成级 3（在线发布小模型服务） | 要经过 CI 构建与契约测试门禁 |

## 对接小模型的统一形态（目标，尚未实现）

对接前先把各服务规整到同一套形态：

| 项 | 统一到什么 |
|---|---|
| 接口描述 | 每个服务提供机器可读的接口描述，工具由它派生，不手写第二份 |
| 错误结构 | 统一带可读 `error` 字段（已有约定，`docs/design.md` 的服务契约） |
| 能力清单 | 由各服务的 `/models` 与 `registry/<name>.yaml` 汇总，工作台侧聚合展示 |
| 上限声明 | 各服务把输入上限（行数、字符数、体积、并发）暴露给调用方，便于调用前自查 |
| 鉴权 | 保留服务侧的开关能力，本阶段不开 |

**不改**各服务现有的对外契约字段语义；规整是补齐与统一，不是重命名。

## 决策记录

| 编号 | 决策 | 理由 | 状态 |
|---|---|---|---|
| P1 | 能力资产两段式：镜像出厂基线 + 卷用户能力，卷覆盖基线，可恢复出厂 | **平台内写的 skill/extension 必须活过 Pod 重启**（重启本身可以接受，重启不能丢东西），同时出厂能力要能随 tag 回滚 | 已定 |
| P2 | 平台入口需要登录（单密码或用户名 + 密码），小模型侧本阶段不加鉴权 | 入口后面是能执行任意代码的工作台，属"单个门"问题；小模型侧沿用 D15–D17 | 已定 |
| P3 | 云端 provider 的地址与密钥由环境注入，不入仓库、不入镜像 | 密钥纪律与 cops 现有密钥路径一致 | 已定 |
| P4 | 不做能力市场 | 单用户场景下收益为零，成本是长期维护面 | 已定 |
| P5 | 本阶段不对接现有小模型，先规整 API 再统一对接 | 避免"接一次改一次" | 已定 |
| P6 | 工作台独立仓库、独立镜像，不做 modelman 的一个服务 | 生命周期、信任等级、状态形态都不同 | 已定 |
| P7 | 基线更新到已被本地改过的能力时保留本地版并提示，不静默覆盖也不阻断启动 | 静默覆盖会丢用户改动；阻断启动会让一次镜像升级变成故障 | 已定 |
| P8 | provider 配置环境为基线，平台内可覆盖，覆盖写卷 | 日常改 provider 不必走 cops 改密钥 + 重启 | 已定 |
| P9 | 登录只输密码，不做账号体系 | 单用户场景下用户名只是形式 | 已定 |
| P10 | 会话与物料保留 90 天、目录上限 2 GB，超限按最旧回收 | 落盘路径必须有数值，否则会日积月累写满（推理侧第 4 条约束） | 已定 |
| P11 | 工作台部署在 cloud3 的 k3s，由 cops 增加一个单元 | 与 modelman 同机；大模型在云端，工作台自身占用小 | 已定 |
| P12 | extension 发布需一次确认，reload 失败自动回退上一可用版本 | 级 2 是可执行代码，热加载失败不能让平台停在半坏状态 | 已定 |
| P13 | 本阶段只做 UI，不额外开放程序接口 | 端点复用即可，多开一个面向程序的接口就多一套待维护的鉴权与限流 | 已定 |
| P14 | 本阶段不做定时/后台任务 | 等出现具体闭环需求再引入调度，避免常驻组件 | 已定 |
| P15 | 工作台以 **fork pi-web** 为骨架：面 A 会话与部分面 B 能力复用上游，不自建第二套 | 面 A（会话列表、续流、分支、工具渲染、花费展示）是最耗时也最不值得重写的一块，上游已完整；自建还要先造一遍同样的形态 | 已定 |
| P16 | agent 仓库就是 pi-web 的 fork（上游 `agegr/pi-web`），我们的代码只放固定目录并登记分叉面；与 modelman 只共享约定、能力清单、交付形态，无代码共享、单向依赖无环 | fork 要能持续 merge 上游；两个仓库的构建链与密钥面完全不同；modelman 不知道 agent 存在，是两边各自独立发版与回滚的前提 | 已定 |
| P17 | 镜像能力基线只放"没有它就不算工作台"的能力，其余走卷按需加；基线越小越好 | 基线是要 review、要跟上游 merge、每次重建都要验的东西；卷上的能力可随时增删 | 已定 |

## 待定问题

| 问题 | 影响 | 建议默认 |
|---|---|---|
| 小模型 API 规整的具体形态与完成时点 | 决定 P5 之后对接的启动条件 | 先冻结一份"统一形态"清单，再逐个服务改 |
| 工作台的资源上限（内存 / CPU）与卷容量 | cops 侧的限额声明 | 待实测后给数值 |
| 会话记录与物料的导出包格式 | 归档入口的实现 | 单个 tar，内含 manifest 与会话原文 |
| 本地大模型服务何时做（`docs/roadmap.md` 里的时序预测同样排队中） | 主机内存分配 | 等 provider 用量与成本数据出来再定 |
